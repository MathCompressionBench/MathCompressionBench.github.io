In short

A taskTarget theorems in a Lean library; you compress their proofs.
Cannot changeThe background, and the target (its statements and the definitions they use; proofs inside those may change). Editable: everything else.
Counted once eachThe target proofs and every non-background declaration they reach, statement and proof (an inductive type with its constructors and recursor).
FreeTarget statements, library references (one node each, plus universe levels), running tactics.
ValidThe kernel re-checks everything. Statements and definitions stay unchanged. Only allowed imports and axioms may be used.
ScoreNfinal; fewer wins.

Exact definition

Score: proof-term node count

The score is the number of nodes in the kernel proof terms of everything charged. Fewer wins.

The formula, sum by sum
N = Σtargets t N(proof t) + Σlemmas, definitions d [ N(statement d) + N(body d) ] + Σinductive types I [ N(type I) + Σconstructors c N(type c) + N(I.rec type) + Σrules r N(r) ]

What is charged

KindWhat countsFor example
Target proofsOnly the proof of each target theorem; its statement is free.theorem target … := by rw […]: the term rw leaves
Helper lemmasEvery lemma in the task's files that a charged proof uses, directly or indirectly: statement and proof, once however often it is used.theorem double (n : Nat) : n + n = 2 * n := …
Definitions usedFor definitions, instances and structures in the task's files that a statement or proof uses, we count the type and value once. Those a statement uses are the target's definitions. Proofs inside them may change.the toy task's def add : MyNat → MyNat → MyNat and instance : Add MyNat, used by its statements through +
Declarations Lean generatesEquation lemmas (f.eq_1), auxiliary proofs (_proof_1), match and casesOn definitions are charged like any declaration when something charged uses them.rw [f] uses f.eq_1
Inductive typesUsing the type, any constructor or a projection charges the type, every constructor and its recursor. Each pays its type, and the recursor also pays its rules, one per constructor.inductive MyNat | zero | succ (n : MyNat): see below
An inductive type, expanded

For an inductive type Lean generates its recursor MyNat.rec, the principle of proof by induction and definition by recursion. Its rules say what it computes on each constructor: MyNat.rec z s zero = z and MyNat.rec z s (succ n) = s n (MyNat.rec z s n). The table gives the counter's numbers for this file.

Other generated declarations, such as MyNat.casesOn, count only when something charged uses them.

How the nodes of a term are counted

Each kernel node costs as below, plus its children.

Kernel constructorCounts as
f a (application)1 + N(f) + N(a)
fun x : T => b, ∀ x : T, b1 + N(T) + N(b)
let x : T := v; b (also have)1 + N(T) + N(v) + N(b)
constant c.{u}1 + nodes of its universe levels; the name's length is free
Sort u1 + nodes of u
projection e.i1 + N(e)
bound variable; literal (any size)1
metadata wrapper; binder names and binder info0
a subterm that occurs twicecounted twice
example: @congrArg.{1,1} MyNat MyNat n m succ ih17
The example, node by node
  • applications, one per argument: 6
  • congrArg.{1,1}: 1, plus 2 for each universe level 1 (successor of zero): 5
  • MyNat, twice: 2
  • n, m (bound variables): 2
  • succ: 1
  • ih (bound variable): 1
  • total: 17

What is free

  

    
      
LibraryA reference to a background constant costs one node per use, plus its universe levels. Its own proof is never counted.

      
Target statementsThe statements of the targets.

      
Tactics, metaprogramsRunning them costs nothing. Only the terms they leave are counted, and those are often large.

      
Kernel computationWhat the kernel evaluates while checking (for example decide) is not counted. Only the per-declaration heartbeat limit applies.

      
NamesNames of constants, binder names and binder info.

      
Literal sizeA number or string literal is one node, whatever its size.

Comparing runs

  

    
      
Combining runsOn each task an agent's result is its best run: the smallest verified final node count among its runs. Agents are ranked on each task by it, fewest nodes first; an agent with no verified run on a task ranks last there, and tied agents share the average of the places they take: two agents tied for first both rank 1.5, and agents without a verified run on a task share the last places the same way. The overall ranking is the average rank over the tasks, each task weighted equally; lower is better. Tables count runs without a verified score under “No score”.

Validity

  
Any failed check means rejection without a score.

  

    
      
Kernel replayLean's kernel re-checks every declaration

      
Statementsidentical to the original

      
The target's definitionsEach definition a statement uses is part of the target: its type and value (and those of everything it depends on in the task, proofs inside excluded) must hash to the recorded value. ./check and the verifier both reject a change; the verifier's message “frozen definition changed” means one of the target's definitions changed. No proof is ever compared.

      
Importseditable files and the task's pinned background only

      
Axiomspropext, Quot.sound, Classical.choice only (no sorry, no native_decide)

      
Limitskernel heartbeats per declaration decide the verdict. Memory and wall clock only stop a check, without a verdict

      
Allowedany Lean code, metaprograms included; any proof may change, even one inside the target's definitions

    


  
Your tools: ./check and ./submit

  

    
      
./checkBuilds your files with the task's pinned Lean toolchain, replays every editable file in Lean's kernel within the kernel heartbeat limit per declaration, checks the rules above and counts the nodes. The official verification runs the same code. Nothing is sent anywhere.

      
It printsThe task and its sha256, the scorer version, then the verdict, valid or invalid, with your node count and the original's, followed by a line that compares the two. --verbose also lists what each declaration pays; --json prints the result as JSON.

      
It fails whenA rule is broken: the verdict is invalid, with one line per problem, such as a changed target statement or target definition, an import or axiom that is not allowed, a declaration over the kernel heartbeat limit or a failed build, then the end of Lean's log (exit status 1). A safety limit (wall clock, memory, processes, disk) stops a check with no verdict (exit status 3). Time and memory never decide validity.

      
./submitChecks again, then writes your bundle, submissions/submission-<first 16 hex digits of its ID>.tar.gz: your editable sources, the kernel terms they compile to, the node count and hashes, and the run's budget and time elapsed. --log DIR adds your log, --tokens-json FILE your token usage, --track agent|record the kind of run (an agent alone, or any means), which decides the leaderboard tracks it can count on: open, and for an agent run within 60 or 120 minutes agent-60 or agent-120. Nothing is sent anywhere.

      
It printsThe check's result, the bundle's path, its submission ID (the bundle's sha256) and how to submit it: a pull request that adds the bundle to the submissions repository.

      
It fails whenThe check is invalid (“refusing to bundle an invalid submission”, exit status 1), a safety limit stopped the check (no bundle, exit status 3), or --log is not a directory or --tokens-json not a JSON object (exit status 1).

Kinds of change

  


  
Glossary

  

    
      
TargetA theorem the task names, with the definitions its statement uses (target definitions). You compress its proof; its statement, and the types and values of those definitions, must stay exactly as they are.

      
HelperA declaration in the task's own files, other than a target, that a target reaches: your lemmas, the task's definitions and what Lean generates for them.

      
BackgroundThe libraries the task imports, such as Mathlib or Lean's core library. They are free to use and never edited.

      
Target definitionA definition, instance or structure that a target's statement uses, and part of the target. Its type and value must stay the same. Proofs inside it may change (validity).

      
KernelLean's small trusted checker. It re-checks every declaration of a submission, and the terms it checks are what is counted.

      
HeartbeatLean's unit of checking work: a count of small memory allocations, the same on every machine. Each declaration must pass within the task's kernel heartbeat limit.

      
Universe levelThe level of a Sort (Prop is Sort 0, Type is Sort 1), also given to constants such as congrArg.{1,1}. Zero and a level variable are one node each. Each successor adds one, so 1 is two nodes.

      
RecursorThe eliminator Lean generates for an inductive type, such as MyNat.rec, for induction and recursion over that type. Its rules, one per constructor, say what it computes on that constructor.

      
Automatic sharing passA fixed program of MathCompressionBench that writes each repeated subterm of the original proofs once (with let) and changes nothing else. It is a reference point, not an agent.

      
ReceiptThe signed record MathCompressionBench's verifier writes when it checks a submission: its verdict, node count and hashes. A receipt file's sha256 identifies it. Its root hash is one sha256 chained over the task, the submission, its sources, the counted terms, the scores, the verdict and the verifier. Changing any of them changes the root hash.

      
Scorer versionThe version of MathCompressionBench's checking and counting code: a release number, or a release candidate before the release. Every check names the version it used.

      
Study's first checkThe check the study ran on each run's final during its experiments, with the checker it used then, not MathCompressionBench's verifier. A final it rejected could still count as valid when a second check of the same, unchanged file accepted it.

      
Failed, unconfirmedThe study's verdicts on runs without a valid final. Failed: the final source failed a check or did not build. Unconfirmed: the study's records show no checked final source. Both mean no score in the study. This site checks each run's scored file again (which file is scored).

      
AgentA model with its harness and reasoning effort: .

      
HarnessThe program that runs a model as an agent. It hands the model the task files and tools and runs the commands the model asks for.

      
Sharing metaprogramLean code an agent writes into its submission that, like the automatic sharing pass, writes each repeated subterm once; allowed, and only the terms it leaves are counted.

      
Task packageThe files a participant gets for a task: the Lean project with its editable files and the scripts that check and score it.
